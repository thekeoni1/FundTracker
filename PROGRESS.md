# FundTracker progress

A dated working log, not documentation of the current code. Every entry records what was true and what was decided on its date and is not edited afterwards, except the decisions log, where a wrong decision is changed in place with a dated note saying why.

PLAN.md is the plan and the single source of truth. docs/SESSIONS.md holds the session prompts. This file records what actually happened.

## Decisions log

Settled decisions. A later session should not re-litigate these.

| Date | Decision | Detail |
| --- | --- | --- |
| 2026-10-29 | Stack is Python, requests, SQLite, Flask and HTMX, venv with pinned requirements | Matches ../edgardly so both projects are run the same way. FastAPI, httpx and uv were considered first and dropped for consistency, not on merit. |
| 2026-10-29 | Ingest every Form D of every industry; hedge-fund filtering is a query | Manager linking needs a filer's PE, VC and other filings too, and the whole corpus is small. Classification rules can change without re-ingesting. |
| 2026-10-29 | Backfill from the earliest quarterly data set available | "Never seen before" only means something against full history. Cost is a few MB per quarter. |
| 2026-10-29 | The nightly daily form index is the source of truth for new filings | The Latest Filings Atom feed is noisy (mixes DEF 14A forms, repeats filings per CIK) and shallow. It is optional for intraday refresh only. |
| 2026-10-29 | Quarterly data sets and per-filing XML load into the same tables through the same dataclasses | Both carry the same fields with different encodings. The rest of the app never knows the source. |
| 2026-10-29 | The inbox unit is a launch, not a filing | Master, feeder and offshore vehicles file together and would otherwise show as three rows. |
| 2026-10-29 | Newness is rule-based with visible reasons and tunable weights, no ML | About 8 hedge fund new notices a day. The user must be able to trust and tune the ranking. Weights live in one dict. |
| 2026-10-29 | Every ingestion step is idempotent and recorded in ingest_log | Running anything twice yields the same database. Missed nights heal through catchup. |
| 2026-10-29 | Tests never touch the network | Real filings are saved as fixtures; HTTP is mocked. Same rule as edgardly. |
| 2026-10-29 | User-Agent is read from .env and never committed | SEC policy requires a real name and email. |
| 2026-10-29 | Child rows are numbered from 1 per accession in both sources | The XML parser numbers issuers, related persons, recipients and signatures from 1 in document order. The data set SEQ_KEY values start at 101, so the TSV loader renumbers from 1 in SEQ_KEY order. A filing loaded from either source then writes identical rows, which is what makes the cross-source parity test possible. Closes open question 8. |
| 2026-10-29 | Exemption code `06` means Rule 506(b) | Filings before the 2013 rule change carry `06` where later ones carry `06b` or `06c`. Scoring and filters treat `06` as 506(b). From open question 1. |
| 2026-10-29 | Entity stems are compared as sorted token sets, and also exactly | AQR files entity names with the halves reversed (open question 6). Sorting tokens makes "MANAGEMENT AQR CAPITAL" and "AQR CAPITAL MANAGEMENT" one key without weakening exact matches. The sorted-set key is stored beside the stem, not instead of it. Applies in WP4. |
| 2026-10-29 | WP2 and WP3 run in sequence in one implementation session, not in parallel | There is one working tree and no remote, and both packages touch ingest.py, cli.py and schema.sql. Parallel sessions would collide. |
| 2026-10-29 | A filing's filing_date from the daily path is the index row's Date Filed, not the index file's date | A filing can be listed in a later day's index than its Date Filed (AQR, 0001635511-15-000001, is in form.20150616.idx with Date Filed 20150615, as in the data set). Using the row's date keeps XML and data set rows equal. The index file's date stays the ingest_log key for the day, since catchup walks index files. Closes open question 12. |
| 2026-10-29 | Daily form index rows are parsed from the right, not by the header's column offsets | The header is unchanged since 2009, but from 2025 the data columns sit five characters to the right of it (Form Type widened from 12 to 17). Every row ends with CIK, an 8-digit Date Filed and an edgar/ path, and form types never contain two spaces in a row. All rows of 17 real indexes from 2009 to 2026 parse. |
| 2026-10-29 | catchup walks every weekday from an anchor and skips days already logged ok or no_index | The anchor is the day after the last data set filing date, else the earliest daily day logged, else 30 days ago. Starting after the latest logged day cannot refill a deleted or failed day in the middle, which the WP3 exit criteria require. A normal run still fetches only new days. |
| 2026-10-30 | An ingest_log row records what has been loaded for its key across all runs | A rerun that loads nothing leaves an existing ok or no_index row untouched. A rerun that loads something (a filing that reached the index after the first fetch) adds to n_rows, updates finished_at and keeps the first run's started_at. A rerun that fails leaves an existing ok row in place and reports the failure in the log output only; status becomes error only when there is no earlier ok row. Backfill already skips quarters marked ok, so a rerun leaves their rows alone. Found in WP3 step 5, where daily reruns had overwritten three days' counts with 0. |
| 2026-10-30 | EDGAR's AccessDenied 403 means the file does not exist | EDGAR answers a missing daily index (weekend or holiday) with 403 and an S3 style `<Error><Code>AccessDenied</Code>` XML body, never 404. EdgarClient returns such a 403 at once, without retrying, and `is_not_found` is true for it and for 404; a 403 without that body (SEC's HTML "Undeclared Automated Tool" page) is still throttling and keeps the retry path. daily logs no_index for either. Detection is on the body, never the status alone, and lives in the client so every caller gets it. Found in WP3 step 5, where 2026-10-12 (Columbus Day) was logged as error after five retries. |

## Open questions

Numbered, dated, closed in place with the answer and the date.

1. (2026-10-29) Which schema versions other than X0708 appear in Form D XML filed since 2009, and which elements differ? Only matters for the XML path, which handles recent filings; the data sets flatten older ones. Resolve in WP1 by sampling. Closed 2026-10-29: sampled the first D filings on one mid-June day per year from 2009 to 2025, plus 8 each on 2010-06-15 and 2015-06-16 and all 225 X0708 filings on 2026-10-27. Versions seen: X0401 (2009), X0704 (2010, 2011), X0705 (2012), X0706 (2013), X0707 (2015 to 2017), X0708 (2018 onward). No older version uses an element name or nesting that X0708 lacks; the differences between files are only which optional elements a filer filled in. All of them parse with the X0708 parser, and the X0704 and X0707 fixture tests list every field that comes back None, the same set an X0708 filing gives when it leaves the same elements out. One difference in meaning, not structure: filings before the 2013 rule change use exemption code `06` (Rule 506), where later ones use `06b` or `06c`. WP4 scoring should treat `06` as 506(b). 2014 was not sampled.
