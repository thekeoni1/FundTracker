# FundTracker session prompts

One prompt per work session, each a record of what was asked for as of its date. What actually happened is in PROGRESS.md. Each prompt is self-contained: paste it into a fresh Claude Code session in the FundTracker folder and it loads its own context before doing anything.

Rules of use:

- Do not start session N+1 until session N's exit criteria are met and recorded in PROGRESS.md.
- Every session begins by reading PLAN.md, PROGRESS.md and docs/edgar-formd-reference.md, and ends by updating PROGRESS.md.
- Tests never touch the network. Real filings go into tests/fixtures.
- One commit per numbered step, in order. Plain prose, no em dashes, in every doc and user-visible string.

## Session 4. Derived layer, classification, scoring and the `new` command (WP4)

Do not start until Session 3's exit criteria are recorded (they were, 2026-10-30). Read PLAN.md (sections 6 derived tables, 7.1 to 7.4, 8 CLI, 9 WP4), PROGRESS.md in full (decisions on `06`, on sorted-token-set entity keys, and questions 6, 11 and 13 in particular), and docs/edgar-formd-reference.md section 2. This session turns 784,472 raw filings into funds, managers and launches, scores each launch for newness, and gives the user a `new` command they can read every morning. No UI, no network, no change to the raw tables or to ingestion.

Design points that are settled, so build them as written:

- Derived tables are rebuilt from scratch by `derive` on every run, inside one transaction, in seconds to a few minutes. `review` is never rebuilt. Add the derived tables to `db/schema.sql` with `CREATE TABLE IF NOT EXISTS`; `derive` deletes their rows and refills them rather than dropping tables, so `review` foreign keys and the user's own indexes survive.
- Identifiers must be stable across rebuilds so `review` rows keep pointing at the same thing. `manager_id` is `m` plus the CIK of the cluster member with the earliest `first_filing_date` (ties: lowest CIK). `launch_id` is the accession of the earliest `D` filing in the launch (ties: lowest accession). A fund belongs to exactly one launch, the one at its first filing.
- Exemption codes are normalised before any rule looks at them: `06` becomes `06b` (pre-2013 Rule 506 filings, see the decisions log). Store the normalised list in `fund.exemptions`.
- Linking keys per CIK, each with the earliest filing date it appears on, in a derived table `link_key(kind, key, cik, first_date)` with an index on `(kind, key)`:
  - `entity_stem`: `normalize.entity_stem` of every related person with `is_entity = 1`.
  - `entity_tokens`: the same stem as a sorted, space-joined token set, so AQR's reversed halves match (question 6). Both kinds are written for every entity, and a match on either links.
  - `signer`: `signature.signer_norm`, skipped when it equals the issuer's own `norm_text(entity_name)` or is an entity by `normalize.is_entity`.
  - `phone`: issuer phone reduced to digits, skipped when shorter than 7 digits.
  - `address`: `normalize.address_key(street1, zip)` of the primary issuer.
  - Skip empty keys, keys of fewer than 4 characters, and a stoplist of generic stems (`GENERAL PARTNER`, `MANAGING MEMBER`, `MANAGEMENT`, `CAPITAL`, `PARTNERS`, `ADVISORS`, `N/A`, `NONE`, `SAME AS ISSUER`); keep the stoplist as a module constant and extend it with whatever the real run shows. `phone` and `address` keys shared by more than 50 distinct CIKs are dropped as service-provider keys (registered agents, administrators, law firms) and the number dropped is logged; `entity_*` and `signer` keys are never capped, because a large manager legitimately has hundreds of funds.
- Managers are the connected components of the graph whose nodes are CIKs and whose edges are shared `link_key` rows, found with union-find in Python. `manager.key_kind` records which kind of key gave the component its first edge; a CIK with no shared key is its own single-fund manager. `display_name` is the most frequent `entity_stem` among the manager's keys, else the most frequent `signer`, else `normalize.fund_family_stem` of the earliest fund's name. `first_seen_date` is the earliest `filing_date` of any filing of any member CIK, from any industry.
- Launches group funds of the same manager whose `first_filing_date` fall within 30 days of the launch's `window_start` (walk the manager's funds in date order; a fund more than 30 days after the current window start opens a new launch). Funds with a single-fund manager are also grouped with other single-fund managers sharing the same `fund_family_stem` within 30 days, which folds master/feeder/offshore trios that name no common related person. Launch rows are built for every fund whose latest `industry_group` is `Pooled Investment Fund`, with `fund_type` carried on the launch, so the CLI filter `--type hedge|all` is a query, not a rebuild.
- Classification (`classify.py`) follows PLAN.md 7.1 exactly. `candidate_reason` is a short code: `hedge_fund`, `other_fund_3c`, or empty. The exclusion list for `Other Investment Fund` names is a module constant of regular expressions (real estate, REIT, SPV, co-invest, credit opportunities, private equity, venture, buyout, growth equity, infrastructure, secondaries, BDC, CLO, feeder of a PE/VC name) with a test per pattern.
- Newness score (`newness.py`) follows the table in PLAN.md 7.4 with the weights in one dict named `WEIGHTS`, including the three penalties as negative entries. Definitions: "no linking key seen in any prior filing" means the manager has no filing (any CIK, any industry) dated before `window_start`; "every fund has exactly one filing" is `n_filings = 1` for all funds in the launch; sale yet to occur is true if any fund has it; nothing raised is `total_amount_sold_num = 0` and `n_investors = 0` on every fund; newly formed is `year_of_inc_choice = withinFiveYears` with the year equal to the calendar year of `window_start` or the year before; `06c` and the minimum-investment band (100,000 to 1,000,000 inclusive) are checked on any fund. Penalties: the manager has 5 or more funds whose `first_filing_date` is before `window_start` (-30); any signer title contains `CHIEF COMPLIANCE OFFICER` and the manager has at least one earlier fund (-10); any fund name matches the PE/VC/real-estate patterns from `classify.py` (-20). Clamp to 0 to 100. `newness_reasons` is a JSON list of `{"code": ..., "points": ..., "detail": ...}` in the order applied, so the UI can show why.
